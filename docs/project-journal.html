Components and how they fit

API and database foundation

Main server uses standard-library HTTP routing under /api; Postgres connection uses pgxpool. Health probes the database rather than reporting success merely because the process is running. Config comes from environment variables, with root .env for local development; never publish its contents. Future business features will separate handlers, services/transactions, repository interfaces, and generated sqlc internals.

Identity and browser security Planned

Google OIDC will identify users by issuer + subject, not email. Server-side sessions use a hashed token and a __Host-session cookie with Secure, HttpOnly, SameSite=Lax and Path=/; logout deletes the session. Frontend and API share one origin, avoiding CORS, while exact Origin matching guards mutating requests. Dev login must be omitted from production binaries and must reuse the session creation path. Implementation ticket.

Events and trackers Planned

Common event fields live in life_events; vacations and purchases have detail tables. Trackers are long-lived definitions with immutable dated entries. Pausing/resuming logs history rather than resetting a counter invisibly. Deletes are permanent, while a planned event is cancelled. Application transactions ensure event/detail pairs; database constraints enforce ownership and valid relationships where possible. Read-side “today” comes from the user's IANA time zone in Go.

Reminders and Telegram Planned

Reminder rules attach to events; delivery attempts have their own history. A Go polling worker is the initial scheduling strategy, with River deferred until retry/backoff complexity justifies it. Recurrence preserves local wall-clock time across daylight saving changes. Telegram is v1's notification channel; other channels are deferred. See reminder rules and scheduler.

Deployment Planned

Destination is Kubernetes on a self-managed VPS, single public origin and Traefik routing /api to Go. A goose migration Job and separate migrator/app database roles are required; image, manifests, TLS, backups and operational details remain to be decided. No production rollout is recorded. Map.

Choices and reasons

Decision IDs and authoritative wording are in the database decision log. This index summarizes what each choice solves.

Platform, authentication and delivery · D1–D9

D1–D3: Go on a self-managed VPS with eventual Kubernetes replaces the abandoned AWS-managed approach; the frontend is a separate, still-unselected application.

D4: Google OIDC with issuer/subject identity avoids treating a changeable email as the account key and leaves room for another identity provider.

D5: sqlc + pgx keeps complex SQL explicit instead of fitting it into an ORM.

D6: Start with a Go ticker; River is deferred until retry/backoff complexity warrants it.

D7–D9: Telegram only in v1; WhatsApp is deferred because of templates/terms risks, while email and web push are dropped from v1 due to delivery and VAPID/service-worker overhead.

Events and tracker history · D10–D19

D10: Derive user-facing dates in Go from the user's time zone, never SQL CURRENT_DATE.

D11–D12: App transactions enforce event/detail pairing; changing an event's kind deletes and recreates it instead of updating kind in place. Manual SQL or a buggy query can still create a mismatch; this risk was accepted.

D13–D16: Trackers have ACTIVE/PAUSED status; pausing logs an end/relapse, resuming logs a fresh start, and paused trackers remain visible with a pause date rather than a counter. This preserves streak history.

D17–D18: START/RELAPSE/OCCURRENCE entry kinds and uniqueness per tracker, date and kind prevent accidental duplicate entries while allowing different kinds on the same day.

D19: No equivalent duplicate constraint for other events: two purchases on one day can be legitimate.

Reminders, deletion and attachments · D20–D27

D20–D21: Reminders belong to events, never trackers. Stopping a reminder marks it cancelled with a stopped-at timestamp, preserving its original planned end and satisfying schedule constraints.

D22–D24: Deletes are permanent and cascade to dependent rows; planned events are cancelled, trackers can be paused or permanently deleted, account deletion erases immediately, and Telegram endpoints are normally disabled instead of deleted to preserve delivery history.

D25: Recurrence uses local wall-clock calculations across DST and clamps nonexistent month days rather than adding fixed 24-hour periods.

D26: Drop unused tracker mode because only one mode was reachable.

D27: Attachments are plain links; Google access tokens are not stored in v1.

Sessions, infrastructure and date reads · D28–D32

D28: Server-side sessions in HttpOnly cookies permit revocation without exposing tokens to JavaScript.

D29: goose plain-SQL migrations run as a Kubernetes Job before deployments.

D30: One public origin, https://events.poulomi-subhayan.click, with frontend at / and API at /api; a host-only Secure cookie avoids cross-origin CORS and cookie-domain sharing.

D31: Exact trusted Origin on POST/PUT/PATCH/DELETE guards against requests from sibling subdomains that SameSite alone would allow.

D32: Read queries accept “today” calculated in Go; SQL/views do not calculate user-local today independently.

Still open

  • When changing an event type by delete/recreate, decide whether tags, attachment links and reminders move to the new event or are deleted with the old one.
  • API shapes, pagination/filtering and error conventions; deployment details, observability, CI/CD and backups. See open technology questions for version/library decisions that must be raised when relevant.
